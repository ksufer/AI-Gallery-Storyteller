# 图片同步功能实现计划

## 现状与约束

- **后端**：[server/index.ts](server/index.ts) Express 5，[server/db.ts](server/db.ts) better-sqlite3（images / tags / image_tags），[server/organizer.ts](server/organizer.ts) 负责 `uploads/YYYY-MM-DD` 归档与 `syncImagesWithDb`。
- **删除行为**：`DELETE /api/images/:id` 与 `POST /api/batch/delete` 会删除物理文件并调用 `deleteImage(id)`，需在删除时同步更新 `sync_records.status = 'deleted'`，避免再次同步时重新复制。
- **前端**：无路由，单页 + 弹窗（如 [SettingsModal.tsx](components/SettingsModal.tsx)）；无 WebSocket/SSE 库，已有 generate-story 的 SSE 用法可复用。
- **技术选型**：不引入 Bull/BullMQ，在单进程内用异步循环 + 暂停标志实现“后台任务”；进度采用 **SSE** 推送（与现有 stream 风格一致），前端轮询作为降级。

## 一、数据库层

**文件**：[server/db.ts](server/db.ts)

- 在 `initDb()` 中新增三张表（与需求中的 SQL 一致）：
  - `sync_sources`：id, name, path, enabled, last_sync_at, auto_sync, sync_interval, created_at
  - `sync_records`：id, source_id, source_path, file_hash, file_size, file_mtime, target_path, status, copied_at, error_message；唯一约束 (source_id, file_hash)；索引 file_hash、status
  - `sync_tasks`：id, source_id, status, total_files, processed_files, total_size, copied_size, started_at, completed_at
- 新增方法（示例命名）：
  - `createSyncSource`, `getSyncSources`, `updateSyncSource`, `deleteSyncSource`
  - `getSyncRecordsBySourceId`, `upsertSyncRecord`, `markSyncRecordDeletedByFilePath(filePath)`（按 `target_path` 匹配并置 status='deleted'），`resetDeletedRecordsBySourceId(sourceId)`（清空该源下 status='deleted' 的记录，用于“重置同步记录”）
  - `createSyncTask`, `updateSyncTaskProgress`, `getActiveSyncTaskBySourceId`
- **删除联动**：在 `deleteImage(id)` 被调用处（仅 server 端）不修改 `db.ts` 的 `deleteImage` 本身，而在 [server/index.ts](server/index.ts) 的 `DELETE /api/images/:id` 和 `POST /api/batch/delete` 中，在调用 `deleteImage` 之后调用 `markSyncRecordDeletedByFilePath(image.file_path)`，实现“应用内删除即标记为 deleted”。

## 二、同步核心服务

**新文件**：`server/syncService.ts`

- **路径与安全**
  - 路径校验：对用户输入的源路径做 `path.resolve` + `fs.realpathSync`，校验目录存在且可读；禁止目标路径指向或包含 `uploads` 根目录外的写入（目标固定为现有 `UPLOADS_DIR`）。
- **扫描**
  - `scanSourceDirectory(sourcePath, options)`：递归扫描源目录，只保留图片扩展名（.png/.jpg/.jpeg/.webp）；按 `options.fromDate` / `options.toDate`（基于文件 mtime）过滤；返回 `{ path, mtime, size }[]`。
  - 可选：`options.recursive: boolean`、`options.extensions: string[]`，首版可写死递归 + 固定扩展名。
- **Hash**
  - 使用 `crypto.createHash('sha256')` + `fs.createReadStream` 流式计算，避免大文件占满内存；仅对“需要判断是否已同步/是否被用户删除”的文件计算（见下）。
- **同步记录与去重**
  - 对每个待同步文件：先查 `sync_records` 中 (source_id, file_hash)。若存在且 status='deleted' → 跳过；若 status='copied' 且目标文件存在 → 跳过；若 status='copied' 但目标不存在 → 可视为需重新复制（或仅更新 target_path），首版可简化为“deleted 才跳过，其余都参与复制”。
  - 为控制首轮 50G+ 压力：扫描后得到列表，先不全部算 hash；首版可对“未在 sync_records 中出现过”的文件再算 hash；已存在 (source_id, file_hash) 且 copied 且文件在 → 跳过。
- **复制与目标路径**
  - 目标路径规则与 [server/organizer.ts](server/organizer.ts) 一致：按文件 mtime 得到 `YYYY-MM-DD`，目标目录 `uploads/YYYY-MM-DD`，文件名使用 `getSafeFileName` 防重名；复制用 `fs.copyFile` 或流式 copy，避免整文件进内存。
- **分批与暂停**
  - 每批 50–100 个文件（可配置），批间 `setImmediate` 或短 `setTimeout` 让出事件循环；维护 `inMemoryState: Map<sourceId, { paused: boolean, cancel: boolean }>`，循环内每批前检查 `paused`，若为 true 则挂起直到恢复或取消。
- **任务与进度**
  - 开始同步时插入 `sync_tasks`（status=running），每批更新 `processed_files` / `copied_size`；结束时更新 status=completed/failed、completed_at。进度推送：在内存中维护 `lastProgress[sourceId]`，由单独的 **SSE 端点** 读取并推送（见下），前端订阅该 SSE 显示进度条与日志。
- **错误与日志**
  - 单文件失败：写入 `sync_records.error_message`，status=failed，继续下一文件；可汇总“最近 N 条”日志供前端显示。

**与 organizer 的衔接**：同步只负责“复制到 uploads/日期/文件名”；复制完成后对新增文件调用现有逻辑：先确保目录结构已存在，再在 sync 流程内对每个新写入的文件调用 `parseImageFile` + `upsertImage`（与 [server/organizer.ts](server/organizer.ts) 中 `syncImagesWithDb` 的“新增文件”逻辑一致），这样侧边栏和图库会自动出现新图。无需在同步完成后再全量跑 `syncImagesWithDb`（可选：最后跑一次以修正任何遗漏）。

## 三、API 设计

**文件**：[server/index.ts](server/index.ts)

- **源管理**
  - `POST /api/sync/sources` — body: `{ name, path }`，校验 path，创建 `sync_sources`。
  - `GET /api/sync/sources` — 返回列表（含 last_sync_at、enabled、auto_sync、sync_interval）。
  - `PUT /api/sync/sources/:id` — 更新 name/path/enabled/auto_sync/sync_interval、时间范围等（若首版时间范围存在表或配置中）。
  - `DELETE /api/sync/sources/:id` — 删除源（CASCADE 会删 sync_records/sync_tasks）。
- **同步控制**
  - `POST /api/sync/start/:id` — 对 source_id 启动同步（若已有 running 任务则返回 409）；后台异步执行 `syncService.runSync(sourceId)`，立即返回 202。
  - `POST /api/sync/pause/:id` — 将对应 sourceId 的 `paused` 置 true。
  - `POST /api/sync/resume/:id` — 将 `paused` 置 false（若需要单独 resume 端点）。
  - `GET /api/sync/status/:id` — 返回当前任务状态（来自 sync_tasks + 内存进度）：pending/running/paused/completed/failed，processed_files/total_files，copied_size/total_size，最近几条日志。
- **预览与重置**
  - `GET /api/sync/preview/:id` — 仅扫描 + 时间过滤，返回待同步文件数量与总大小（可选列表前 100 条），不复制、不写库。
  - `POST /api/sync/reset-records/:id` — 调用 `resetDeletedRecordsBySourceId(sourceId)`，用于“重置该源的删除记录”。
- **进度推送**
  - `GET /api/sync/events/:id` — SSE：根据 sourceId 从内存中读取 `lastProgress[sourceId]`，以固定间隔（如 1s）或“有更新即推”向客户端发送 JSON 事件（processed, total, copiedSize, totalSize, status, lastLogLine）。前端可复用类似 generate-story 的 EventSource 用法。

**删除联动**：在 `DELETE /api/images/:id` 和 `POST /api/batch/delete` 中，在成功删除 DB 记录后调用 `markSyncRecordDeletedByFilePath(image.file_path)`（对 batch 循环调用）。

## 四、前端 UI

- **入口**：在 [App.tsx](App.tsx) 或 [Sidebar](components/Sidebar.tsx) 中增加“图片同步”入口（如侧边栏底部或设置旁），打开“同步配置/同步管理”视图（可为一独立全屏或大弹窗，与 Settings 类似）。
- **配置页（同步设置）**
  - 源列表：展示 name、path、enabled、最后同步时间；支持添加（输入路径 + 名称）、编辑、删除、启用/禁用。
  - 每个源可配置：时间范围（fromDate / toDate，基于 mtime）、是否自动同步、同步间隔（秒）；首版冲突策略可写死为“保留两者”（getSafeFileName 已做重名处理）。
- **同步页**
  - 按源展示：最后同步时间、待同步数量/预估大小（来自 `GET /api/sync/preview/:id`）、当前任务状态与进度条（processed/total、copiedSize/totalSize）。
  - 操作：开始同步、暂停、恢复；“重置该源删除记录”按钮（调用 reset-records）。
  - 同步日志：显示最近约 100 条（由 status 接口或 SSE 携带的 lastLog 数组提供），实时追加。
- **状态与轮询**：若使用 SSE，则连接 `GET /api/sync/events/:id` 时无需轮询；否则用 `GET /api/sync/status/:id` 每 2s 轮询一次以更新进度条和日志。

## 六、关键实现细节摘要

- **sync_records 与删除**：`target_path` 存复制后的**绝对路径**（与 `images.file_path` 一致），这样 `markSyncRecordDeletedByFilePath(image.file_path)` 可直接用 `WHERE target_path = ?` 更新。
- **大体积与内存**：流式 hash、`fs.copyFile`/流复制、每批 50–100 个文件、不一次性加载全部文件内容。
- **断点续传**：首版可用“暂停后再次点击开始则视为新任务”（重新扫描、已 copied 的会跳过）；若需真断点，可在 sync_tasks 中存“已处理 file_hash 列表”或 last_index，恢复时从断点继续。
- **安全**：路径仅允许本地绝对路径，`realpathSync` 后校验可读；禁止源路径为 uploads 子目录，避免循环。
